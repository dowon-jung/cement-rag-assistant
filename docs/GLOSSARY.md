## 1. AI / LLM 관련

### LLM (Large Language Model)
대규모 텍스트 데이터로 학습된 언어 모델. 자연어 질의를 이해하고 답변을 생성한다.
이 프로젝트에서는 사용자 질의 분류, 뉴스 요약, 최종 답변 생성에 사용한다.

> **왜 Gemma2인가?**
> Google이 공개한 오픈소스 모델로 로컬 서버에서 무료로 실행 가능하다.
> 고객 데이터가 외부로 나가지 않아야 하는 폐쇄망 환경에 필수적이다.
> Claude API(Anthropic) 대비 품질은 낮지만 데이터 보안과 비용 면에서 우위다.

---

### Ollama
로컬 서버에서 LLM을 실행하기 위한 오픈소스 도구. 명령어 한 줄로 Gemma2, Llama 등의 모델을 실행할 수 있다.

> **왜 Ollama인가?**
> GPU 없이 CPU만으로도 실행 가능하다. 설치가 간단하고 모델 관리 명령어를 제공한다.
> 단, 동시 요청 처리 성능이 낮아 사용자가 많은 환경에서는 vLLM으로 교체한다.

---

### vLLM
GPU를 활용해 LLM을 고성능으로 서빙하는 프레임워크. `continuous batching`으로 동시 요청을 효율적으로 처리한다.

> **왜 vLLM인가?**
> 동시 사용자 10명 이상의 프로덕션 환경에서 Ollama 대비 처리량이 5~10배 높다.
> OpenAI API 호환 인터페이스를 제공해 코드 변경 없이 Ollama와 전환 가능하다.

---

### Anthropic API
Anthropic이 제공하는 Claude 모델 API. 가장 높은 답변 품질을 제공하지만 질의 내용이 Anthropic 서버로 전송된다.

> **언제 사용하는가?**
> 내부 PoC 단계나 데이터 보안 요건이 낮은 환경에서 빠르게 시작할 때 사용한다.
> 엔터프라이즈 계약 시 데이터 보존 0일 설정과 학습 미사용 보장을 받을 수 있다.

---

### AWS Bedrock
AWS 클라우드 안에서 Claude를 포함한 여러 LLM을 호출하는 서비스.
고객이 이미 AWS를 사용하고 있다면, VPC 엔드포인트를 통해 데이터가 고객 AWS 계정 밖으로 나가지 않도록 설정할 수 있다.

> **Anthropic API와의 차이점?**
> 데이터가 물리적으로 Anthropic 서버가 아닌 고객의 AWS 계정 내에서 처리된다.
> 보안 요건은 높지만 완전 오프라인은 아닌 고객사에 적합하다.

---

### LLM 백엔드 추상화
`LLM_BACKEND` 환경변수 하나로 Ollama / vLLM / Bedrock / Anthropic API를 코드 변경 없이 전환하는 설계.

```
LLM_BACKEND=local      → Ollama 또는 vLLM (완전 오프라인)
LLM_BACKEND=bedrock    → AWS Bedrock Claude (VPC 격리)
LLM_BACKEND=anthropic  → Anthropic API (인터넷 필요)
```

> **왜 추상화하는가?**
> 고객사마다 보안 요건이 다르다. 코드를 건드리지 않고 납품 환경에 맞게 전환할 수 있어야 한다.

## 2. RAG 파이프라인 관련

### RAG (Retrieval-Augmented Generation)
LLM이 답변을 생성하기 전에 관련 문서를 먼저 검색해서 참고 자료로 제공하는 방식.
LLM이 학습하지 않은 사내 데이터나 최신 정보를 답변에 반영할 수 있다.

```
질문 → 관련 문서 검색 → LLM에게 [문서 + 질문] 전달 → 답변 생성
```

> **왜 RAG인가?**
> LLM을 직접 학습(Fine-tuning)시키는 것은 비용이 크고 데이터가 바뀔 때마다 재학습이 필요하다.
> RAG는 DB에 문서를 넣기만 하면 LLM이 최신 데이터를 참조할 수 있다.

---

### Chunking (청킹)
긴 문서를 LLM이 처리할 수 있는 작은 단위로 나누는 작업.
LLM은 한 번에 처리할 수 있는 텍스트 길이(컨텍스트 윈도우)에 한계가 있어 반드시 필요하다.

이 프로젝트의 청킹 전략 3가지:

| 전략 | 대상 | 방식 |
|------|------|------|
| **Semantic chunking** | PDF 법령/매뉴얼 | 512 토큰 단위, 64 토큰 겹침 |
| **Table-aware chunking** | CSV 가격/통계 | 헤더 + 6행 단위 묶음 |
| **Structured store** | ERP 수치/실시간 API | 청킹 없이 DB 직접 저장 |

> **왜 전략을 나누는가?**
> PDF는 문장 의미가 이어지므로 의미 단위로 자르는 게 정확하다.
> CSV 표는 행과 열의 관계가 중요해서 헤더를 함께 묶어야 수치 의미가 살아난다.
> ERP 집계(전월 대비, 증감률)는 벡터 검색보다 SQL이 훨씬 정확하다.

---

### Embedding (임베딩)
텍스트를 숫자 벡터(768차원)로 변환하는 작업. 의미가 비슷한 텍스트는 벡터 공간에서 가까운 위치에 놓인다.

> **왜 ko-sroberta-multitask인가?**
> 한국어에 최적화된 임베딩 모델이다. 영어 중심 모델 대비 한국어 문서 검색 정밀도가 높다.
> HuggingFace에서 무료로 다운로드 가능하며 로컬 실행이 가능해 에어갭 환경에서도 동작한다.

---

### Adaptive RAG
질의 난이도에 따라 검색 전략을 동적으로 선택하는 방식.

```
단순 질의 → Vector Search만 사용 (빠름, 약 0.8초)
중간 질의 → Hybrid Search 사용 (정확, 약 1.5초)
복잡 질의 → Hybrid + Re-ranker + Query Rewriting (최고 정밀도, 약 3.5초)
```

> **왜 필요한가?**
> 모든 질의에 최고 수준의 파이프라인을 적용하면 단순 질의에도 3초 이상 걸린다.
> 난이도에 맞는 전략을 선택해 응답 속도와 정확도를 동시에 최적화한다.

---

### Self-RAG
검색 결과가 충분하지 않으면 LLM이 스스로 재검색하는 루프.
최대 3회까지 쿼리를 수정하며 재검색을 시도한다.

> **왜 필요한가?**
> 규제 문서처럼 정확도가 중요한 도메인에서 한 번의 검색으로 충분한 근거를 찾지 못할 때가 있다.
> Self-RAG를 적용하면 Faithfulness(답변이 문서 근거에 기반하는 비율)가 향상된다.
> RAG Agent에만 적용하며, 시장 데이터나 뉴스 같은 다른 Agent에는 불필요하다.

---

### GraphRAG
Neo4j 그래프 DB를 활용해 문서 간 관계를 탐색하는 RAG 방식.
벡터 검색으로는 찾기 어려운 "연쇄 적용 조항" 같은 관계 기반 질의를 처리한다.

```
벡터 검색: 유사한 텍스트 조각 찾기
그래프 검색: 법령 → 조항 → 위반 시 → 연쇄 조항 추적
```

> **언제 GraphRAG를 쓰는가?**
> "질소산화물 기준 초과 시 어떤 조항이 연쇄 적용되나?" 같이 조항 간 의존 관계가 필요할 때.
> 단순 키워드 검색으로는 이런 관계 정보를 찾을 수 없다.

---

### Re-ranker (재순위화)
벡터 검색 + BM25 검색으로 추려낸 상위 20개 결과를 Cross-Encoder 모델로 재평가해 최종 5개를 선정하는 단계.

> **왜 필요한가?**
> 벡터 검색과 BM25는 빠르지만 정밀도가 다소 부족하다.
> Re-ranker는 느리지만 정확해서, 후보를 줄인 다음 단계에서만 적용하면 효율적이다.

---

### Query Rewriting (쿼리 재작성)
LLM이 사용자의 구어체 질의를 검색에 최적화된 형태로 다듬는 작업.

```
원본: "유연탄 요즘 얼마야?"
재작성: "유연탄 가격 최근 3개월 추이 USD/톤"
```

> **왜 필요한가?**
> 사용자는 검색 키워드가 아닌 자연스러운 말투로 질문한다.
> 그 말투 그대로 검색하면 관련 문서를 놓치는 경우가 많다.

---

### RRF (Reciprocal Rank Fusion)
벡터 검색 결과와 BM25 검색 결과를 각 문서의 순위를 기반으로 점수를 합산해 통합하는 알고리즘.

> **왜 단순 점수 합산이 아닌 RRF인가?**
> 벡터 점수(0~1)와 BM25 점수(0~수십)의 단위가 달라 직접 합산하면 왜곡된다.
> RRF는 점수 대신 순위를 사용해 두 검색 방식을 공정하게 결합한다.

---

### RAGAS
RAG 시스템의 검색·생성 품질을 자동으로 측정하는 평가 프레임워크.

| 지표 | 의미 |
|------|------|
| Faithfulness | 답변이 검색된 문서에 근거하는가 (할루시네이션 방지) |
| Answer Relevancy | 질의와 답변이 얼마나 관련 있는가 |
| Context Recall | 필요한 문서가 실제로 검색됐는가 |
| Context Precision | 검색된 문서 중 실제로 필요한 것의 비율 |

> **왜 필요한가?**
> 청킹 전략이나 검색 방식을 바꿀 때 체감이 아닌 수치로 개선 여부를 확인할 수 있다.

## 3. 검색 관련

### Hybrid Search (하이브리드 검색)
벡터 검색(의미 유사도)과 BM25 키워드 검색을 결합한 방식.
두 검색을 병렬로 실행한 후 RRF로 결과를 통합한다.

```
Qdrant Vector Search  ─┐
                        ├─ RRF 통합 → 최종 결과
Elasticsearch BM25    ─┘
```

> **왜 둘 다 필요한가?**
> 벡터 검색은 의미가 비슷한 문서를 잘 찾지만 정확한 수치나 고유명사에 약하다.
> BM25는 키워드 일치에 강하지만 동의어나 문맥을 이해 못한다.
> 둘을 결합하면 서로의 약점을 보완한다.

---

### BM25
키워드 빈도와 문서 길이를 고려한 전통적인 텍스트 검색 알고리즘.
"질소산화물 0.004kg/Sm³" 같은 정확한 수치를 검색할 때 벡터 검색보다 정확하다.

---

### nori (노리)
Elasticsearch의 한국어 형태소 분석 플러그인.
"시멘트생산량" → "시멘트", "생산", "량"으로 분리해 검색 정확도를 높인다.

> **왜 Qdrant Sparse Vector 대신 Elasticsearch nori인가?**
> Qdrant의 Sparse Vector는 단순 토큰 기반 BM25라 한국어 형태소 분석이 없다.
> "시멘트배출기준"을 검색할 때 nori는 형태소 단위로 분리해 더 정확한 결과를 반환한다.

---

### Vector Search (벡터 검색)
임베딩 벡터 간의 코사인 유사도를 기반으로 의미적으로 유사한 문서를 찾는 검색 방식.

---

## 4. 데이터 저장소 관련

### Qdrant
벡터 검색 전용 데이터베이스. 문서 임베딩 벡터를 저장하고 유사도 기반 검색을 처리한다.

> **왜 Qdrant인가?**
> Docker로 간단히 실행 가능하고 무료 클라우드 티어도 있다.
> Payload 필터링(법령명, 날짜 등으로 검색 범위 제한)을 지원해 도메인 특화 검색에 유리하다.

---

### Elasticsearch
전문 검색(Full-text Search) 엔진. 이 프로젝트에서는 nori 플러그인을 활용한 한국어 BM25 검색에 사용한다.

> **왜 별도로 필요한가?**
> Qdrant는 벡터 검색에 특화돼 있고 한국어 형태소 분석을 지원하지 않는다.
> Elasticsearch의 nori 플러그인이 한국어 키워드 검색 품질을 크게 향상시킨다.

---

### PostgreSQL
관계형 데이터베이스. 수치 데이터, ERP 로그, 실시간 API 응답 영구 저장에 사용한다.

> **왜 수치 데이터는 PostgreSQL인가?**
> "전월 대비 생산량 증감률", "원화 기준 유연탄 원가" 같은 집계 연산은 SQL이 벡터 검색보다 훨씬 정확하고 빠르다.

---

### Neo4j
그래프 데이터베이스. 법령 간 관계(조항 → 위반 → 벌칙)를 노드와 엣지로 저장한다.

> **왜 그래프 DB가 필요한가?**
> 규제 조항은 다른 조항을 참조하거나 조건부 연쇄 적용되는 구조를 가진다.
> 이런 관계를 벡터 검색이나 SQL로 표현하기 어렵고, 그래프 탐색이 자연스럽다.

---

### Redis
인메모리 키-값 저장소. TTL(Time-To-Live)을 설정해 API 응답을 일정 시간 동안 캐시한다.

> **왜 Redis 캐시가 필요한가?**
> 외부 API(한국은행, 네이버, 기상청)는 매 요청마다 호출하면 느리고 요청 횟수 제한에 걸릴 수 있다.
> Redis에 1시간 또는 30분 캐시를 두면 반복 요청 시 즉시 반환이 가능하다.

---

### TTL (Time-To-Live)
캐시 데이터의 유효 기간. 설정한 시간이 지나면 자동으로 삭제된다.

| 데이터 | TTL | 이유 |
|--------|-----|------|
| 환율 | 1시간 | 한국은행 하루 1회 고시 |
| 뉴스 | 30분 | 속보성이 있어 자주 갱신 |
| 날씨 | 1시간 | 기상청 3시간 단위 발표 |

---

## 5. 메시지 큐 관련

### Kafka
분산 메시지 스트리밍 플랫폼. 수집기(Producer)가 데이터를 발행하면 처리기(Consumer)가 비동기로 소비한다.

> **왜 Kafka인가?**
> PDF 인덱싱, LLM 요약 같은 무거운 작업을 API 요청과 분리해 비동기로 처리할 수 있다.
> 처리기가 다운되더라도 메시지가 토픽에 보존되어 재기동 시 이어서 처리 가능하다.
> Consumer 수를 늘려 처리량을 수평 확장할 수 있다.

---

### Topic (토픽)
Kafka에서 메시지를 분류하는 단위. 우편함과 비슷한 개념으로, Publisher는 특정 토픽에 메시지를 발행하고 Consumer는 해당 토픽을 구독한다.

이 프로젝트의 토픽 9종:

| 토픽 | 목적 |
|------|------|
| `market.raw` | 환율 수집 완료 (모니터링·알림 전용) |
| `news.raw` | 뉴스 수집 완료 → LLM 요약 트리거 |
| `weather.raw` | 날씨 수집 완료 (모니터링 전용) |
| `erp.updated` | ERP 배치 완료 → DB 저장 트리거 |
| `indexing.requests` | 문서 인덱싱 요청 |
| `indexing.results` | 인덱싱 완료 알림 |
| `llm.requests` | LLM 비동기 처리 요청 |
| `llm.results` | LLM 처리 완료 결과 |
| `dlq.errors` | 처리 실패 메시지 보관 |

---

### DLQ (Dead Letter Queue)
처리에 실패한 메시지를 따로 보관하는 큐. 실패 원인을 분석하거나 재처리하기 위해 사용한다.

> **왜 필요한가?**
> PDF 파싱 오류나 임베딩 실패 시 메시지를 그냥 버리면 데이터 손실이 생긴다.
> DLQ에 보관하면 실패 원인을 파악하고 수정 후 안전하게 재처리할 수 있다.

---

### Consumer Lag
Kafka Consumer가 발행된 메시지를 얼마나 뒤처져서 처리하고 있는지를 나타내는 수치.
Lag이 크면 처리 속도가 발행 속도를 따라가지 못하고 있다는 의미다.

> **이 프로젝트에서 어떻게 활용하는가?**
> Kubernetes KEDA 스케일러가 Consumer Lag이 100 이상이 되면 Consumer Pod를 자동으로 늘린다.
> 이를 통해 트래픽이 증가할 때 자동으로 처리 용량이 확장된다.

---

### KRaft 모드
Kafka가 ZooKeeper 없이 자체적으로 클러스터를 관리하는 방식. Kafka 3.3 이후 기본 모드.

> **왜 KRaft인가?**
> ZooKeeper를 별도로 구성·관리할 필요가 없어 운영이 단순해진다.

---

## 6. 인프라 / 배포 관련

### LangChain
LLM 애플리케이션 개발을 위한 Python 프레임워크. 프롬프트 관리, Tool 연결, 메모리 등 공통 기능을 제공한다.

---

### LangGraph
LangChain 위에서 동작하는 상태 기반 워크플로우 프레임워크.
Agent들의 실행 흐름을 DAG(방향 있는 비순환 그래프)로 정의한다.

> **왜 단순 Chain이 아닌 LangGraph인가?**
> 이 프로젝트처럼 질의 유형에 따라 실행 경로가 달라지고, 루프(Self-RAG 재검색)가 필요한 경우 LangGraph의 조건부 엣지와 상태 관리가 필수적이다.

---

### FastAPI
Python 기반 고성능 웹 프레임워크. `async/await` 기반으로 동시 요청을 효율적으로 처리한다.

> **왜 FastAPI인가?**
> 비동기 처리로 LLM 응답 대기 중에도 다른 요청을 받을 수 있다.
> Pydantic 모델로 요청/응답 스키마 검증이 자동화되고 Swagger 문서가 자동 생성된다.

---

### SSE (Server-Sent Events)
서버에서 클라이언트로 데이터를 스트리밍 방식으로 전송하는 기술.
LLM 토큰이 생성될 때마다 즉시 화면에 출력되어 응답이 빠르게 느껴진다.

> **왜 SSE인가?**
> LLM이 전체 응답을 생성한 후 한번에 보내면 사용자는 수초간 빈 화면을 기다려야 한다.
> SSE로 토큰을 스트리밍하면 첫 글자가 나오는 시간(TTFT)이 줄어 체감 속도가 크게 향상된다.

---

### Docker / Docker Compose
애플리케이션을 컨테이너로 실행하는 도구. 모든 서비스(Qdrant, PostgreSQL, Elasticsearch 등)를 동일한 환경에서 실행할 수 있다.

---

### Kubernetes (K8s)
컨테이너 오케스트레이션 플랫폼. Pod 자동 재시작, 롤링 업데이트, HPA 자동 스케일링을 제공한다.

---

### HPA (HorizontalPodAutoscaler)
CPU 사용률이나 커스텀 메트릭을 기준으로 Pod 수를 자동으로 늘리거나 줄이는 K8s 기능.
이 프로젝트에서는 API Pod는 CPU 기준으로, Kafka Consumer Pod는 Consumer Lag 기준으로 스케일 아웃한다.

---

### KEDA (Kubernetes Event-Driven Autoscaling)
Kafka Consumer Lag 같은 이벤트 기반 메트릭으로 K8s Pod를 자동 스케일링하는 도구.
기본 HPA는 CPU/메모리만 지원하는데, KEDA로 Kafka Lag 기반 스케일링이 가능해진다.

---

### StatefulSet
K8s에서 데이터베이스처럼 상태(데이터)가 있는 애플리케이션을 배포할 때 사용하는 리소스.
Pod가 재시작되어도 동일한 PersistentVolume에 연결되어 데이터가 보존된다.

> **Deployment와의 차이?**
> Deployment는 상태 없는(Stateless) 앱에 사용하고, StatefulSet은 PostgreSQL, Qdrant, Elasticsearch, Kafka 같은 상태 있는(Stateful) 앱에 사용한다.

---

### Harbor
기업 내부용 컨테이너 이미지 레지스트리. Docker Hub 대신 사내 서버에서 이미지를 저장하고 배포한다.

> **왜 필요한가?**
> 에어갭 환경에서는 Docker Hub에 접근할 수 없다.
> Harbor에 이미지를 사전 저장해두면 인터넷 없이 K8s 배포가 가능하다.

---

## 7. 모니터링 관련

### Prometheus
시스템 메트릭을 수집하고 저장하는 모니터링 도구. 15초마다 각 서비스의 메트릭을 수집한다.

---

### Grafana
Prometheus에서 수집한 메트릭을 시각화하는 대시보드 도구.
API 응답 시간, LLM 호출 횟수, Kafka Lag, 캐시 hit/miss율 등을 실시간 차트로 확인할 수 있다.

---

### LangSmith
LangChain/LangGraph로 구성된 Agent의 실행 흐름을 추적하는 Anthropic 자회사 서비스.
각 Agent 호출 시간, 프롬프트 내용, 토큰 사용량을 시각화한다.

> **에어갭 환경에서는?**
> LangSmith는 외부 SaaS라 폐쇄망에서 사용 불가능하다.
> Jaeger + OpenTelemetry로 동일한 기능을 내부에 구축한다.

---

### Jaeger
분산 추적(Distributed Tracing) 오픈소스 도구. 요청이 여러 서비스를 거치는 흐름을 시각화한다.
에어갭 환경에서 LangSmith 대체재로 사용한다.

---

### OpenTelemetry
애플리케이션 추적(Trace), 메트릭, 로그를 수집하는 표준 인터페이스.
FastAPI, httpx 같은 라이브러리에 자동 계측(Auto-instrumentation)을 적용하면 코드 수정 없이 트레이스가 수집된다.

---

### TTFT (Time To First Token)
LLM이 첫 번째 토큰을 반환하기까지 걸리는 시간. SSE 스트리밍 환경에서 체감 응답 속도를 나타낸다.

---

### TPS (Tokens Per Second)
LLM이 초당 생성하는 토큰 수. 값이 클수록 빠른 응답 속도를 의미한다.

---

## 8. 에어갭 / 보안 관련

### 에어갭 (Air-gap)
인터넷이 완전히 차단된 폐쇄망 환경. 시멘트·철강 같은 제조업 고객사에서 보안 정책상 흔히 요구된다.

> **이 프로젝트의 에어갭 대응 전략:**
> `AIRGAP_MODE=true` 환경변수를 설정하면 외부 API 호출 대신 내부 DB 조회로 자동 전환된다.
> 모든 Docker 이미지, LLM 모델, Python 패키지, Elasticsearch nori 플러그인을 사전에 반입한다.

---

### AIRGAP_MODE
이 프로젝트의 폐쇄망 전환 스위치. `true`로 설정하면 모든 외부 네트워크 호출이 차단되고 내부 데이터만 사용한다.

---

### devpi / Nexus
사내 PyPI 미러 서버. 인터넷이 없는 환경에서 Python 패키지를 설치할 수 있도록 내부 패키지 저장소를 구축하는 도구.

---

| **Prometheus + Grafana** | ELK, Datadog | 오픈소스, 자체 호스팅, K8s 친화적 |
| **Jaeger** | Zipkin, LangSmith | 오픈소스, 에어갭 가능, LangSmith 대체 |
| **Harbor** | Nexus Registry | Docker Hub 대체, 에어갭 필수 |
| **KEDA** | 기본 HPA | Kafka Lag 기반 스케일링 지원 |

### 이 프로젝트에서 하지 않은 선택

| 방향 | 하지 않은 이유 |
|------|---------------|
| 단일 Vector DB만 사용 | 한국어 형태소 분석 없이 BM25 품질이 낮아 ES 병행 |

| 단일 LLM 백엔드 고정 | 고객사마다 보안 요건이 달라 추상화 필요 |
